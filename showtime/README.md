# showtime 显示界面：黑胶播放页 + 时钟页

把 AkuBox 那块 **162×132 的 SPI 小屏**（ST7735S）从"只有时钟"改造成两种界面：

| 播放中 | 停止 5 秒后 |
|---|---|
| ![黑胶播放页](screenshots/player-vinyl.png) | ![时钟页](screenshots/clock.png) |
| **圆形旋转封面**（黑胶唱片，不显示歌名） | **大号白色时间** + 顶部状态行 |

两图均为真机 `/dev/fb0` 抓帧，6 倍最近邻放大。

---

## 播放页（黑胶模式）

专辑封面**逆时针旋转**，像唱片一样：

| 参数 | 值 |
|---|---|
| 圆盘直径 | 130px（可见行 0..130、x 16..146，水平居中偏满） |
| 转速 | 24°/秒（约 15 秒一圈）；30fps 下每帧 0.8°，看不出台阶 |
| 渲染 | 30fps（`VINYL_FRAME_S = 0.033`） |
| 采样 | 逆映射 + **双线性插值**（非最近邻，转起来不会有锯齿跳动） |
| 遮罩 | 圆外直接跳过不画 → 天然圆形，无需后处理 |
| 文字 | **不显示歌名/歌手**，整个版面让给封面 |

**暂停/结束时立即停转**，并**停在当前角度**（不清零）——恢复播放接着转，像被手按住又放开。
角度按 `CLOCK_MONOTONIC` 累加，只在真正 `playing` 时推进，所以任何卡顿都不会让唱片"跳角度"。

## 时钟页

- 时间用**高度优先**排版：字号 `TIME_FONT_SIZE = 100`（字形高约 91 行，几乎撑满状态行以下空间），
  再用 FreeType 的**水平变换矩阵**压窄到屏宽内 —— 实测自然宽 360 → 压缩 **43%** → 渲染 **141×91**。
  这是**非等比方放**（数字明显瘦高），因为宽度是硬约束：等比放大的上限就是原来那样，想更高只能压窄。
  压缩后竖向笔画仍有 4-5px 宽，不会压断。
- 颜色**白色**（原来是绿色）。
- **日期与星期已移除**，版面全部让给时间。
- 顶部状态行：`vol:NN%`（左）、充电图标（中右）、电量 `NN%`（右）。冒号保持原厂的**闪烁**行为。

FreeType 会把变换同时作用到**字形轮廓与 advance** 上，所以测宽、定位、绘制三者自动一致：

```c
FT_Matrix m = { .xx = 65536L * pct / 100, .xy = 0, .yx = 0, .yy = 65536L };
FT_Set_Transform(fr->face, &m, NULL);   // 之后的 get_text_width / draw_text 都带上它
... 绘制 ...
FT_Set_Transform(fr->face, NULL, NULL); // 必须复位，否则影响后续电量/音量绘制
```

## 数据从哪来

不需要 MQTT，也不需要 Home Assistant 自动化。sendspin 协议本身就把元数据送到了设备：
客户端的 `MetadataRoleListener::on_metadata()` 收到 `title / artist / album / artwork_url`，
本仓库的 `patches/0003-sendspin-client-nowplaying-bridge.patch` 把它们写成 `key=value` 小文件：

```
state=playing
title=红尘客栈
artist=周杰伦
album=十二新作
artwork_url=http://192.168.101.75:8095/imageproxy/0103cf…?size=512&fmt=jpg
```

showtime 每秒读一次。这不是新增通道，只是把客户端**已经收到**的信息落到磁盘。

## 性能：别让屏幕吃掉整个 CPU

这块 ARMv7 是**单核 1GHz**，提帧率必须先把耗时量清楚。实测踩过两个坑，都不是"画得慢"：

### 坑 1：厂商代码每帧 fork 一条 shell 管道（最大的一笔）

`get_current_volume_s()` 内部是：

```c
snprintf(cmd, sizeof(cmd), "amixer get 'Power Amplifier' | grep 'Mono:' | awk '{print $2}'");
fp = popen(cmd, "r");        // 一次调用 = fork 4 个进程（sh + amixer + grep + awk）
```

它在循环顶部**每帧**调用。1fps 时是 1 次/秒尚可忍受，30fps 就是 **30-64 次 fork/秒**，
实测白烧掉 **~60% 单核**。症状很具有欺骗性：`/proc/stat` 显示 96% 忙，
但进程表只解释 35% —— 缺的那些全在"短命进程"里，两点采样抓不到，
要看 `/proc/stat` 的 `processes` 字段算 **fork 速率**才暴露。

修法：音量文字只在时钟页显示，把查询挪进时钟分支即可（1 次/秒）。**fork 速率 64 → 0.9 次/秒。**

### 坑 2：这颗 CPU 的 VFP 是串行高延迟 → 逐像素必须用定点整数

先用 `CLOCK_PROCESS_CPUTIME_ID` 分开量"绘制"与"刷屏"：**draw 14-19ms/帧、flush 0.3ms**，
瓶颈全在绘制（SPI 带宽不是瓶颈）。再实测浮点能力：**1e6 次 float 乘加要 70ms**（约 70 周期/次），
双线性每像素 30+ 次浮点 → 1.3µs/像素。

改为定点：旋转矩阵 16.16、采样坐标 16.16、双线性权重 **8 位小数**（乘积不溢出 int32），
并**直写后备缓冲**（垂直翻转每行只算一次，不再逐像素调 `fb_write_pixel`）。
**每帧 14-19ms → 2.6-4.4ms（约 4-5 倍）。**

> **坑中坑**：`sx_fp = iw<<16/(2R)` 已是 16.16 比例因子，`ui * sx_fp` 出来就是 16.16 像素坐标，
> **不能再 `>>16`**。多移一次会把结果降回"±R 单位"，`x0` 在全屏只抖 0~1 像素，
> 整张图退化成采样中心一个像素 —— **封面变成一片纯色**。自检：打印几个点的 `ui` 与 `x0`，
> `ui` 差 21 则 `x0` 必须差 ≈21。

### 帧率：先量再定档

| 帧周期 | 实测帧率 | showtime CPU | 说明 |
|---|---|---|---|
| `0.020` | 50.0 fps | **36%** | 每帧反而涨到 5.7-8.3ms，高帧率下内核刷屏与 WiFi 争抢 |
| `0.025` | 39.96-40.02 fps | 20-23% | |
| **`0.033`（当前）** | **30.09-30.28 fps** | **16-17%** | 24°/秒 转速下每帧仅 0.8°，看不出台阶 |

每帧成本各档几乎一致（0.53% vs 0.56% CPU/fps），说明省下来的就是帧数本身。
50fps 花 3 倍 CPU 换不来可感知的顺滑，所以定档 30fps。

另外：帧调度按**绝对时间对齐下一帧**，而不是"渲染完再固定 sleep"——
后者会把渲染耗时叠进帧周期，帧率随负载漂移，转起来一抖一抖。

### 总体

| 阶段 | showtime | 整机 |
|---|---|---|
| 厂商原版时钟（1fps） | ~1% | ~10% |
| 提到 30fps、**未修 fork 风暴** | 57% | **96%** |
| 修复后（30fps + 定点 + 无 fork 风暴） | **16-17%** | **21-23%** |

时钟页仍按秒刷新，几乎不占 CPU（实测 **0%**）。

## 关键实现点

| 点 | 说明 |
|---|---|
| **帧缓冲是上下翻转的** | `fb_write_pixel()` 里 `mirrored_y = height - 1 - y`。所以**代码里 y 越大越靠屏幕上方**，可见行 ≈ `131 - (y + 字号)`。最初按"y 越大越靠下"写，结果标题跑到顶部、歌手被挤出屏幕外 |
| `draw_text` 与 `draw_image` 的 y 含义不同 | 前者是**基线**（字形落在 y 之上），后者是**顶边**（往下铺）。同一个 y 值两者差半个字高 —— 充电图标原先因此比电量文字低 6 行还多挂 12 行 |
| 封面尺寸只认 80/160/256/512 | MA 的 imageproxy 只接受这几个尺寸（128/120/100 都返回 400），统一请求 `size=160&fmt=png` |
| 必须用 PNG | URL 里 `fmt=jpg` 是默认值，但设备只链接了 libpng；PNG 由 MA 现场转码提供 |
| 缩放 | 用**面积平均**（160 → 130 降采样），比最近邻干净 |
| 缓存 | 按 `url_hash(重写后 URL)` 缓存到 `/tmp/showtime-cover-cache/`，同一首重播不再下载 |
| 降级 | 封面下载/解码失败就画深灰圆盘，不影响可用性 |
| 时钟回退 | 停止满 **5 秒**才回时钟；5 秒窗口内保持封面，避免切歌瞬间闪回时钟 |

## 怎么验证（别只看代码对不对）

> **验证必须检查"内容"，不能用代理指标。** 踩过：用「非黑占比 >40% = 黑胶模式」判断，
> 但**一片纯色圆盘也是 62% 非黑** —— 封面已经退化成纯色了，三项检查全部"通过"，
> 只能靠人眼看屏幕才发现。
>
> 可靠做法：**比较屏幕区域与源图的平均颜色**（旋转不变，一个数就能定性），
> 正常应差 <60/765。实测修好后：屏幕 rgb(78,90,98) vs 源图 rgb(80,91,100) = **5**。
> 再辅以「不同颜色数」（正常上千；纯色盘只有 1~2）与「最大单色占比」。

其余可数值化的检查：

| 检查 | 做法 | 实测 |
|---|---|---|
| 圆形遮罩 | 圆外一圈的非黑像素数 | **0** |
| 中心黑点 | 圆心半径 6 内暗像素数 | **0** |
| 在转 | 相隔 1 秒两帧的差异像素数 | 12251 |
| 暂停冻结 | idle 后 1 秒 vs 3 秒两帧差异 | **0** |
| 回时钟 | idle 后 3 秒 vs 7 秒两帧差异 | 15002 |

**比对基准必须是"此刻屏幕上那张"**：从写 `nowplaying` 到抓帧之间，只要真实播放还在跑，
客户端就可能因切歌重写该文件，屏幕随之换封面 —— 此时拿旧 URL 去比会得到假失败
（实测踩过：差异 290，实际渲染完全正确）。做法：先看缓存目录里有没有**新的**（按 mtime）
缓存文件，或先确认播放已结束（`fuser /dev/snd/pcmC0D0p` 为空）再手写状态。

## 安装

```bash
sudo bash install-showtime-nowplaying.sh
```

脚本会装编译依赖、应用补丁、编译、备份并替换二进制、重启服务。

**前置条件**：`patches/0003-sendspin-client-nowplaying-bridge.patch`（本仓库 `patches/`）
需要已装上 —— 它负责写 `/var/lib/sendspin-client/nowplaying`。
没装也能编译运行，只是永远显示时钟，不会出错。

**两种安装方式**（脚本自动选择，`--force-build` 可强制源码编译）：

```bash
# A. 预编译（约 5 秒）：--bin 指定，或放到 showtime/prebuilt/showtime.armv7 自动使用
sudo bash install-showtime-nowplaying.sh --bin /tmp/showtime.armv7 -y

# B. 源码编译（默认）：需要厂商源码 + gcc 开发包
sudo bash install-showtime-nowplaying.sh -y
```

预编译路径会校验 `ELF 32-bit ARM` 与 `ldd` 无缺失才部署，只适用于**同型号**设备。
源码编译需要 `/opt/aku/showtime/showtime.c`；部分固件批次只发二进制（例如 MQTT 版，
没有消息时屏幕全黑、也没有源码）—— 这种设备直接用上面的预编译路径，从另一台同型号
AkuBox 复制二进制即可：

```bash
scp root@<另一台>:/opt/aku/showtime/showtime /tmp/showtime.armv7
```

> 本仓库只提供补丁与脚本、不重新分发厂商二进制；`prebuilt/` 目录默认空的，
> 由你自己放入（详见 [prebuilt/README.md](prebuilt/README.md)）。

编译依赖：`libfreetype-dev libpng-dev libcurl4-openssl-dev pkg-config`

## 回滚

```bash
systemctl stop showtime
cp -a /opt/aku/showtime/showtime.pre-nowplaying /opt/aku/showtime/showtime
cp -a /opt/aku/showtime/showtime.c.pre-nowplaying /opt/aku/showtime/showtime.c
systemctl start showtime
```
